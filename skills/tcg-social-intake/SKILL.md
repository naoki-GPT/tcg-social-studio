# 第1工程：案件の前提を確認する

版：1.0.0／2026-11-13。**誰に、何のために、何を1つ作るか**を制作前に固定する。最新の会話と関係する案件資料を読み、制作フォルダに `01_intake.md` と `01_intake.json` を残す。フォームをユーザーに丸投げせず、既知の情報を自分で埋める。

## 1. 今回の依頼と操作範囲を確定する

- 案件名と用途を最初に確認する。共通試作は共通試作として扱い、特定の店の在庫・販売条件・アカウントを混ぜない。参考店と依頼先を区別する。別途進行中の専用制作は対象外にする。
- 「1つ」は1企画。カルーセルの枚数・動画のカット数とは別。指定数を3案などの既定値で上書きしない。
- 最新の明示指示、当該案件の現在の決定、過去資料の順に照合する。過去に承認されたデザインでも、今回却下されたものはそのまま復活させない。
- 読める場所・変更できる場所・触らない場所を記録する。アクセス禁止の表を開かず、別の接続方法や保存済みコピーで迂回しない。「表の更新禁止」と「閲覧も禁止」は指示どおり区別する。
- ブラウザー禁止ならローカル資料や許可されたAPIを使う。この工程では市場・参考投稿の新規収集、生成、公開、予約、送信を実行しない。後の工程の実行可否は今回の許可範囲として記録する。

## 2. 関連する根拠だけを読む

案件の入口、対象客・目的の決定、直近の採否理由を確認する。本文を読んだ範囲だけ根拠にする。会話は原文の短い抜粋、ローカル資料はファイルと資料日・確認日を残す。資料から見つかったURLを、禁止された接続や不要な全資料調査の入口にしない。

資料の方針、実装の報告、実際の動作確認を区別する。過去の市場価格や成約件数は現在の需要の証拠にせず、第2工程へ再調査対象として渡す。直近に却下された商品は、却下理由と再検討条件を残す。

## 3. 制作条件を根拠付きで埋める

[記録のひな形](assets/intake.template.json)を制作フォルダへコピーする。各項目を次の4種類に分ける。

| 状態 | 意味 | 必要な記録 |
|---|---|---|
| confirmed | 今回の指示、または引き継げる案件資料で確認した条件 | 値と根拠ID。資料由来なら資料日と今回への適用理由 |
| proposed | 今回の試作を具体化するための仮置き | 値と理由。ユーザー了承済みと書かない |
| unknown | 次へ進む判断に必要だが決まっていない | 分からない理由と、必要なら短い質問 |
| deferred | 後の工程で判断するため、今は決めない | 決める工程と必要な材料 |

必須項目は、案件／用途、対象客、対象市場、目的、主な行動、企画数、商品の調査範囲。対象客は「海外の人」だけで済ませず、販売店・再販業者・配信者・収集家など購入用途まで書く。主な行動はDMか商品ページ閲覧など1つを軸にする。

媒体・形式、本文言語、導線の実URL、参考の指定、販売条件も記録する。ただし、参考の全枚取得前にカルーセルの枚数を決めない。商品の人気・価格差・割安という結論をこの工程で作らない。未確定の在庫・送料・納期は約束にしない。DM相談の企画でそれらが不明なだけなら商品調査は進められる。

複数案件のどれか不明な場合など、結果を大きく変える質問だけまとめて聞く。共通試作と明示されていれば対象店を再質問しない。可逆的な選択は理由付きの提案として進めてよいが、実店舗の条件や許可を推測で補わない。

## 4. 次工程への引き渡しを検査する

```powershell
python <このスキルの場所>/scripts/validate_intake.py <制作フォルダ>/01_intake.json --out <制作フォルダ>/01_intake_check.json
```

- 案件・用途と企画数は confirmed が必要。それ以外の必須項目は confirmed または理由付き proposed なら調査へ渡せる。必須項目の unknown／deferred は質問または前提整理へ戻す。
- 構造検査が通っても、原文と照らして対象客・案件・制約・提案の区別を読み直す。スクリプトは資料の真偽、アクセス実態、需要や訴求の品質を判定しない。
- 未確認項目を「今ないと商品選定できないもの」と「訴求・制作・公開前に必要なもの」に分ける。すべての空欄を開始条件にしない。
- 次工程には対象客・市場・目的・行動・商品調査範囲・却下理由・操作制約を渡す。後の工程で前提を変える場合は、この記録を更新して再検査する。

## 成果物と終了条件

Markdownには①今回の前提表、②根拠、③未確認と確認する工程、④操作範囲、⑤次工程への指示を載せる。JSONと値・状態をそろえ、検査結果も保存する。

**工程ごとの依頼ではここで止まり、前提をユーザーが確認できる形で返す。** 全制作を依頼された場合は、`ready_for_selection: true` と内容の照合を確認して親の `$tcg-social-studio` の第2工程へ続ける。この記録の存在だけを合格としない。工程ごとの停止を、通常の制作依頼すべてへの追加承認として適用しない。

返答では「確定したこと」「仮置き」「今は決めないこと」と次工程を短く示す。記録が不足していれば前提確定済みとは報告しない。
