# Museで進める運用の設計案

2026-11-13。以下は目指す運用であり、連携済み・自動実行可能という報告ではありません。

| 工程 | 主な担当 | 次に渡すもの | 次へ進む条件 |
|---|---|---|---|
| 目的設計 | Muse | 客、国、買い手の用途、売るもの、主な行動、禁止事項を整理した前提記録 | 確定・提案・未確認が区別されている |
| 商品の需要調査 | Muse | 同条件の候補比較、売れた証拠と期間、費用を踏まえた買う理由 | 人気キャラや相場表だけで選んでいない。根拠不足は未採用 |
| 参考と訴求の調査 | Muse | 対象客に合う参考、全文の訴求分析、全ページ／全編の原素材 | 高い再生数だけで採らず、何を伝え何をさせるか説明できる |
| 制作仕様への分解 | Codex、Museが内容照合 | 文字、配置、色、書体、時刻、効果、置換素材、本文と導線 | 観察した事実と制作提案を分け、参考を省略していない |
| 画像・動画制作と検品 | Codex | 完成全枚／MP4、英語本文と日本語訳、編集元、比較資料、検査結果 | 全出力を開いて確認し、未再現部分を消していない |
| 承認待ちとして記録 | Muse | 企画ID、版、完成物への参照、本文、投稿先、希望日時 | 書き込みを許された新しい管理先がある。記録後に読み戻す |
| 人間が承認 | 利用者 | 承認者・時刻・対象版・対象アカウント・本文・公開日時 | 曖昧な「OK」を別案や変更後の版へ流用しない |
| 投稿と結果確認 | Muse | 投稿ID・URL・実際の公開日時・状態 | 承認対象と一致。投稿後に公開物を確認。失敗と結果不明を分ける |

「直近の伸び」を調べる場合、投稿日時、観測日時、経過時間、再生等の指標、通常投稿との比較条件を残します。1回の観測では伸び率を測れません。伸びを証明できなくても、具体的な訴求や構成の参考として採る理由は別に記録できます。

## 受け渡しの単位

1企画を1つの案件フォルダで扱い、企画IDと版を全資料に付けます。需要の根拠と参考画像はコード本体へ埋めず、MuseとCodexの両方がアクセスできる案件用の保存先へ置きます。保存先の接続は各環境で確認します。

制作への入力は、前提、採用商品と根拠、参考原本の全ファイル、参考の分解表、実際の商品画像、本文・画面内文字、サイズ・尺です。未確定の販売条件は未確定と書きます。足りないファイルを推測で再生成して埋めません。

制作からの出力は、編集元、全完成物、本文、比較用資料、検品結果、未解決事項です。共有する画像／動画と本文のハッシュを承認記録に含める設計を推奨します。具体的なデータ形式とMuseの呼び出し方法は移行作業で実装します。

## 承認と投稿

提案する状態は `draft → producing → needs_review → approved → publishing → published`。差し戻しは `needs_changes`、失敗は `failed`、送信後に結果が分からない場合は `publish_unknown` とします。この状態管理コードはまだありません。

承認後にメディア、本文、投稿先、価格、日時を変えたら承認を失効させます。投稿の重複を防ぐため、企画ID・版・投稿先で一意の処理キーを持つ設計にします。タイムアウト時は投稿一覧や取得可能な投稿IDを照合してから再送可否を判断します。

GitHubはソースと手順の管理場所です。人間が確認する完成物一覧と公開可否の管理は、指定された新しい管理表等で行います。新しい表の作成やSNSアカウント接続は今回のリポジトリ作成には含みません。
